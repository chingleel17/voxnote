## Context

`src/pages/meeting.ts` 目前使用 `transcriptUtteranceRe` 將 `[MM:SS 講者X] 文字` 渲染為時間與文字列。原始版與校稿版可依 `Recording` 分段渲染，因此時間戳能透過錄音 ID 找到頁面上的 `audio[data-recording-id]`；手動版則只儲存一份合併後的 `manual_content`，進入編輯時直接改用單一 `textarea`，會失去分段、講者控制與時間戳互動。

講者對應資料本來就以 `(recording_id, speaker_label)` 為鍵，但 CSS 顏色只由 `speaker-A` 至 `speaker-H` 決定，導致不同錄音段落的同名代號呈現相同顏色。全螢幕容器已採 flex column，內容 body 也有 `flex: 1`，但內容本身與捲動責任未統一，短內容看起來集中在上方，編輯與窄視窗的可用空間也未明確分配。

本變更不需要新的外部 API 或套件；瀏覽器 DOM、既有音訊元素與既有手動版儲存介面足以完成。

## Goals / Non-Goals

**Goals:**

- 在前端建立可往返轉換的逐字稿編輯模型，支援逐列文字、講者及拆分操作，又不改變持久化格式。
- 保留每列所屬錄音 ID，使編輯模式中的時間戳能精確選擇錄音來源。
- 讓講者色彩在單一錄音段落內一致、跨段落可區別，並同時套用於逐字稿與講者對應區。
- 讓檢視、結構化編輯與純文字編輯共用清楚的未儲存狀態及取消/儲存語意。

**Non-Goals:**

- 不建立精確到字詞的時間對齊，也不允許直接修改時間戳。
- 不自動推斷拆分後第二列的真實開始時間。
- 不將跨錄音段落的講者 A 自動判定為同一位真人；真人對應仍由既有講者對應功能決定。
- 不新增逐字稿資料表、JSON 編輯文件格式、歷史版本或自動儲存。
- 不改變原始版、校稿版、匯出與 AI 校稿的格式契約。

## Decisions

### D1：使用暫存列模型，儲存時序列化回既有純文字

結構化模式使用前端暫存模型表示一列：`recordingId`、`segmentIndex`、`time`、`speakerLabel` 與 `text`。進入模式時解析手動內容，編輯操作只更新此模型；切到純文字時序列化，純文字變更可安全解析時再重建列模型，最後仍透過既有 `onSaveManualTranscript(content, baseVersion)` 儲存。

選擇此方案是因為 `manual_content` 已被複製、匯出、摘要與既有版本邏輯使用，改成新 JSON schema 會擴大 Rust、SQLite 與匯出相容範圍。替代方案是新增結構化 JSON 欄位，但目前需求不需要任意時間編輯或複雜字幕 metadata，不值得引入 migration 與雙格式同步。

### D2：以基底版本的分段順序恢復手動列的錄音歸屬

建立手動版時內容源自原始版或校稿版，兩者皆可由 `getGeneratedTranscriptSegments()` 取得分段文字。結構化編輯初始化時，先按手動版的 `manual_base_version` 取得每段錄音及其 utterance 順序，再以保留的段落邊界和列順序建立 `recordingId` 關聯。序列化時保留既有 `MERGED_BREAK_SEPARATOR` 或段落邊界，使後續重新開啟仍能辨認錄音段落。

若既有手動內容已被純文字方式大幅改寫而無法可靠對回段落，結構化模式不得猜測錄音來源，改為保留內容並導向純文字模式。替代方案是把找不到歸屬的時間戳一律綁第一段錄音，但這會讓點擊播放錯誤音訊，違反使用者用音訊校稿的目的。

### D3：雙模式共用單一草稿來源並採明確同步邊界

全螢幕編輯狀態保存 `draftText` 與可選的 `draftRows`。結構化操作後立即更新 rows，需要切換模式或儲存時才序列化為文字；純文字輸入則更新 `draftText`，切回結構化時執行解析。解析失敗時維持純文字內容與模式，不覆寫舊 rows，並顯示無法安全結構化的提示。

此設計避免同時讓 textarea 與多個 row input 各自成為真相。替代方案是每次鍵入都雙向同步，但頻繁完整解析容易造成游標跳動，也會使自由格式內容在輸入尚未完成時被判定失敗。

### D4：講者候選項限於錄音段落，允許顯式新增代號

每列的講者選擇器先列出該 `recordingId` 在基底逐字稿、目前草稿列與既有講者對應中出現的代號。新增講者使用明確動作產生該段下一個未使用的 `講者X` 代號，避免讓使用者輸入任意名稱而混淆「ASR 代號」與「參與者姓名」。真人姓名仍由講者對應區管理。

替代方案只允許既有候選項，但無法處理 ASR 完全漏掉第二位講者；直接列出其他段落代號則會模糊 mapping 的錄音範圍。

### D5：拆分採文字游標位置，新列沿用時間但可立即換講者

每個結構化列使用 textarea 或等效可取得 selectionStart 的文字欄位。拆分動作驗證游標兩側皆有非空白內容，將後半建立在原列之後，複製 `recordingId`、`segmentIndex`、`time` 與目前講者，再將焦點移至新列講者控制或文字欄位。沿用時間只表示可播放參考，不宣稱是精確時間。

替代方案要求使用者先選取後半段再按拆分，操作成本較高；自動估算新時間則缺少字詞級時間資訊，容易產生虛假精度。

### D6：色彩索引由錄音段落與講者代號共同決定

建立穩定的 scope key：`${recordingId}::${speakerLabel}`，再依會議內已排序的 recording index 與 speaker index 映射至一組足夠且可循環的 CSS 色彩變數。DOM 使用 `data-speaker-scope` 或產生的安全 class 套用樣式；逐字稿列、結構化選擇器與講者對應標籤共用同一 helper。

色盤循環時仍以段落標題或 badge 作為第二辨識線索，不能只靠顏色。替代方案動態雜湊成任意 HSL，較難保證在深色與淺色主題下都有足夠對比。

### D7：全螢幕 body 負責配置，內容容器負責捲動

panel 維持 `height: 100%` 的 column flex；body 設為可縮的 `flex: 1; min-height: 0`，檢視器、結構化 editor shell 與純文字 textarea 都設為 `flex: 1; min-height: 0`。檢視器或 editor list 自己設定 `overflow-y: auto`，頁尾保持固定。窄視窗時允許頁尾按鈕換行，避免按鈕被裁切。

替代方案讓整個 panel 捲動會使版本分頁及儲存按鈕離開畫面，不利於長篇逐字稿持續編輯。

## Risks / Trade-offs

- [既有純文字手動版缺少可靠段落邊界] → 只在能安全解析及對應錄音時啟用結構化 rows；失敗時完整保留文字並使用純文字模式。
- [新增講者後既有講者對應區沒有立即出現該代號] → 儲存後重建逐字稿區塊，從更新後手動內容補入候選；實作時讓 mapping 的來源同時考慮手動草稿或已儲存手動內容。
- [色盤有限，很多錄音段落時可能重複] → 段落標題與段落 badge 永遠顯示，色彩只作輔助辨識，並以可讀對比優先。
- [切換純文字模式可破壞結構] → 切回結構化時先驗證且不做破壞性正規化；使用者仍可直接儲存自由格式手動版。
- [拆分列共用時間可能讓兩列跳到同一位置] → UI 明示這是播放參考，規格禁止產生不存在的精確時間。
- [直接呼叫頁面既有 audio 元素可能找不到來源] → 不使用第一段 fallback；顯示提示並保持草稿，避免播放錯段。

## Migration Plan

1. 先加入解析、序列化、錄音歸屬與講者 scope helper，不更動持久化資料。
2. 將全螢幕編輯入口改成模式選擇，保留純文字 editor 作為 fallback。
3. 加入結構化列操作、指定錄音播放與共用講者樣式。
4. 調整全螢幕 flex/overflow 與窄視窗樣式。
5. 以既有手動版、由原始版新建、由校稿版新建、多錄音段落及自由格式內容驗證往返相容性。

回復時可移除結構化模式與新樣式，既有 `manual_content` 不需回滾或資料轉換，仍可由原純文字 editor 開啟。
