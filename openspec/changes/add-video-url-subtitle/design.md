# 設計：影片連結字幕產生

## 處理流程

```
使用者貼上連結
  → yt-dlp 取得音訊（不下載視訊）
  → voxnote_asr /v1/audio/transcriptions（整支一次送出）
  → 解析分段 start/end → 組裝字幕時間軸
  → 落盤（影片項目：來源 URL、標題、逐字稿、字幕時間軸）
  → 浮動字幕視窗呈現
```

與批次逐字稿流程的差異僅在**第一步**（音訊來源由本機檔案改為影片連結）與**最後一步**（產出字幕時間軸而非純逐字稿）。中段的轉錄呼叫完全沿用既有路徑，不另建轉錄實作。

### 客戶端是否需要 ffmpeg（前置驗證項）

上圖刻意**未**包含客戶端的 ffmpeg 轉檔步驟。既有的 ffmpeg 使用全部位於服務端（`server/app.py:92` 起的解碼與前處理），Tauri 客戶端目前未使用 ffmpeg。

服務端在收到上傳音訊後本來就會以 ffmpeg 解碼為 16 kHz 單聲道，故客戶端再做一次轉檔多半是多餘的——只要 `yt-dlp` 輸出的格式為服務端可解碼者即可直接上傳。若成立，本變更只需 `yt-dlp` 一個 sidecar，不需在客戶端引入 ffmpeg。

任務 0.4 即為驗證此點。若驗證失敗（例如 yt-dlp 輸出格式服務端無法處理），才回頭加入客戶端 ffmpeg，屆時相依與打包體積都會顯著增加。

## 關鍵決策

### 為何不沿用會議記錄的資料表

會議記錄帶有與會人員、語者分離、會議日期等語意，影片項目皆不適用。以 `is_video` 旗標塞入既有 `meetings` 表會讓所有查詢與 UI 都要處理「這筆其實不是會議」的分支，且會議清單會被影片稀釋。獨立資料表較單純。

### 摘要的資料歸屬（實作前需決定）

「重用既有摘要能力」在**呼叫 LLM 的邏輯**上成立，但在**資料層不成立**：`summaries` 表對 `meetings(id)` 有 `FOREIGN KEY ... ON DELETE CASCADE`（`db/mod.rs:90-96`），`get_summary`／`save_summary` 的參數皆為 `meeting_id`。獨立的影片資料表無法直接沿用該表。

三個可行方向，擇一於實作前決定：

1. **影片專屬的摘要欄位**：摘要直接存於影片資料表的欄位。最單純，但摘要的 provider／更新時間等中繼資料需一併複製。
2. **`summaries` 改為多型關聯**：以 `owner_type` + `owner_id` 取代 `meeting_id`，需資料遷移且影響既有會議摘要路徑——風險最高，違反「不修改既有流程」的前提。
3. **影片專屬的摘要表**：與 `summaries` 結構相同但 FK 指向影片表。重複一份 schema，但完全不動既有路徑。

**傾向方案 1 或 3**（皆不影響既有會議摘要）。方案 2 除非日後有第三種可摘要的實體，否則不划算。LLM 呼叫本身無論哪個方案都可重用。

### 為何先做浮動視窗，且拆為兩個變更

使用者明確要求兩種模式都要，但先做浮動視窗。技術上這也是較穩健的順序：

- 浮動視窗的呈現層已存在（即時字幕的 overlay），只需替換「字幕來源」——由音訊擷取改為時間軸推進。
- 內嵌播放器涉及影片平台的嵌入限制、播放器 API 整合、WebView 的媒體支援，變數多且與字幕品質無關。先驗證字幕本身正確，再處理播放整合。

**拆為兩個變更**（本變更 + `add-video-subtitle-embedded-player`）而非一個變更分兩階段：OpenSpec 的變更需所有需求皆實作完成才能歸檔。若內嵌播放器的需求留在本變更，`video-url-subtitle` 就必須等到播放器完成才能進入規格基準，期間本變更持續停留於 `changes/`——這正是本次一併清理的其他變更所出現的陳舊問題。

### 與即時字幕共用字幕視窗

`close_overlay()` 以視窗 label 解析單一視窗實體，即時字幕的基準亦要求「同一時間僅允許一個 session」。影片字幕沿用同一個 overlay，故兩者的**顯示**必須互斥。但影片的擷取與轉錄不佔用該視窗，可與即時字幕並行——規格已就此區分。

### 浮動視窗模式的對齊問題

浮動視窗模式下系統無從得知外部播放器的播放進度，故需要使用者手動對齊起點（例如影片播到 0:00 時按下「開始」）。這是此模式的固有限制，非缺陷——內嵌播放器模式（階段二）才能自動同步。

對齊後系統以本機時鐘推進時間軸。使用者暫停影片時需同步暫停字幕，故 MUST 提供暫停／繼續。

### 時間軸粒度：分段級

服務端補上 `end` 即可滿足字幕需求。逐字級（word-level）時間戳需服務端改用支援該輸出的模型參數，改動較大，而對「看影片配字幕」的體驗提升有限——字幕本就以句為單位顯示。若日後要做卡拉OK式逐字highlight再議。

### `end` 欄位：服務端已提供，缺口在客戶端

原先假設需擴充服務端輸出，經查證為誤：`server/app.py:324-333` 的 `normalize_segment()` 已在其「穩定 API 格式」中同時輸出 `start` 與 `end`。

真正的缺口是 `LocalServerSegment` 未宣告 `end`，而 serde 預設忽略未宣告欄位，故該值一路被靜默丟棄。補上欄位即可，**服務端不需任何修改**。

型別選擇留待任務 0.3 的實測決定：服務端的 `float(raw.get("end", 0.0))` 保證該鍵必定存在，故 `f64` 搭配 `#[serde(default)]` 已足夠；若實測發現某些回應路徑缺漏，再改為 `Option<f64>`。加上 `default` 的理由是避免舊版服務端或未來的回應變體造成整筆解析失敗。

## 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| `yt-dlp` 因平台改版失效 | 無法取得音訊 | 以 sidecar 打包，可單獨更新該執行檔而不需重新發版 |
| 長影片轉錄逾時 | 處理失敗 | 沿用批次的 60 分鐘逾時；待 `add-async-transcription-queue` 完成後改為任務佇列 |
| 影片平台禁止內嵌播放 | 階段二部分影片不可用 | 規格已要求告知並保留浮動視窗模式 |
| 使用者誤以為支援直播 | 預期落差 | 規格要求處理前即偵測並告知 |

## 明確不做（YAGNI）

- 不做批次處理多支影片。
- 不做字幕翻譯（既有即時字幕的翻譯能力不移植至此；若需要另開變更）。
- 不做逐字級時間對齊。
- 不做字幕檔匯出（SRT/VTT）——使用者的需求是在本應用內觀看，匯出非當前需求。
