## Context

即時字幕已可運作，本變更處理三類問題：設定共用造成的語言衝突、批次連線參數不適用於即時節奏、固定視窗切段造成的品質損失。

現況關鍵事實（皆已於程式碼確認）：

- `live_caption/mod.rs:462`、`:467` 兩後端皆傳入 `&config.asr_language`；`config/mod.rs:19,77` 顯示該欄位為批次流程共用且預設 `zh`。即時字幕無專屬語言欄位。
- `asr/mod.rs:282-288` 的 `transcribe_voxnote_asr_bytes` **每次呼叫都重建 `reqwest::Client`**，逾時為 `LOCAL_ASR_TIMEOUT_SECS = 3600`（`asr/mod.rs:7`）、讀取閒置逾時 `300` 秒（`:10`）。這些值出自 commit b35e99c，是為長錄音批次刻意放寬的。
- `live_caption/mod.rs:464` 以 `tauri::async_runtime::block_on()` 在字幕迴圈內同步等待遠端回應。
- `live_caption/mod.rs:432-449` 的滑動視窗雖已取「最新視窗」並丟棄舊樣本，但丟棄量由 `keep_samples` 固定推導，無明確的落後偵測或上限。

## Goals / Non-Goals

**Goals**
- 即時字幕的來源語言與遠端端點可獨立於批次流程設定。
- 遠端轉錄在 3 秒級節奏下不因連線建立成本與過長逾時而劣化。
- 轉錄落後時字幕跟隨當下聲音，記憶體不無限成長。
- 切段依語音邊界而非固定時間。
- 字幕視窗可不攔截滑鼠事件。

**Non-Goals**
- 不改變批次逐字稿的任何行為與參數。
- 不做語者分離（沿用前一變更的決定）。
- 不實作 jt-live-whisper 的字幕轉發（Telegram/Slack 等）、關鍵字警示、雙向模式。
- 不引入 Breeze-ASR-26 至即時字幕。該模型是繁中 fine-tune，與本變更的英文用途相反；它對**批次中文會議**仍有評估價值，但屬另一變更的範圍。

## Decisions

### 1. 即時字幕的語言與端點採獨立設定欄位，而非沿用批次欄位

新增 `live_caption_language`（預設 `auto`）、`live_caption_remote_base_url`、`live_caption_remote_model`。

**理由**：使用者的兩個情境語言相反（批次中文會議、即時英文影片），且模型需求不同（Breeze-ASR 繁中 fine-tune vs. 英文低延遲）。共用欄位無法同時滿足。預設 `auto` 而非 `en`，是因為即時字幕的來源語言可能隨影片變動，讓模型自行偵測比鎖定單一語言更能涵蓋一般情況；使用者仍可明確指定以獲得較佳準確度。

**替代方案**：沿用 `asr_language` 並在即時字幕啟動時覆寫。已否決——覆寫語意隱晦，且使用者無法在 UI 上看出即時字幕實際使用的語言。

### 2. 遠端即時轉錄使用獨立的呼叫路徑與連線策略

新增 `transcribe_live_caption_remote()`，與批次的 `transcribe_voxnote_asr_bytes` 分離，具備：

- **重用 `reqwest::Client`**：於 session 啟動時建立一次，存於 session 狀態，供所有視窗共用，避免每 3 秒重建連線與 TLS 交握。
- **秒級逾時**：逾時上限應與視窗節奏同量級（數秒），而非批次的 3600 秒。逾時即放棄該視窗並繼續，不中止 session。
- **不重試**：即時情境下重試所得的結果已過時，直接丟棄該段。

**理由**：批次的參數是為「單次請求處理數十分鐘錄音、寧可久等也不要失敗」而設；即時的取捨相反——寧可丟一段字幕也不能卡住後續。共用同一函式無法同時滿足兩種取捨，故分離。

**替代方案**：為既有函式加參數。已否決——會使批次路徑承擔即時才需要的分支，且違反「不修改既有批次行為」的邊界。

### 3. 音訊佇列採丟棄最舊樣本的背壓策略

佇列設定明確的上限（以秒數表示）。超過上限時丟棄最舊的樣本，並保留最新音訊。

**理由**：即時字幕的價值在於跟隨當下聲音。轉錄落後時若保留所有音訊，字幕會逐漸落後於畫面且佇列無限成長；丟棄最舊樣本可讓字幕在短暫落後後自行追上。此行為對使用者需可觀察（可透過既有錯誤事件通道提示），避免使用者誤以為漏字是辨識問題。

### 4. 保留重疊滑動視窗，改以相似度去重；VAD 用於即時路徑之外

**修正原先的判斷**：先前規劃「以 VAD 切段取代固定滑動視窗」，經檢視 jt-live-whisper 實作後認定該方向對即時路徑並不成立，改採本決定。

參考實作的事實（`translate_meeting.py`，已逐行確認）：

- 其即時路徑的場景預設為「視窗長度／步進」的**重疊滑動視窗**（`SCENE_PRESETS`，`:1311-1316`）：線上會議 5000/3000 ms、教育訓練 8000/3000 ms、演講簡報 12000/4000 ms、快速字幕 3000/2000 ms。與本專案現行的 5 秒／3 秒同構。
- 其即時路徑**未**使用 VAD 切段。faster-whisper 的 `vad_filter` 在即時參數組中設為 `False`（`:1357`、`:1378`），並註明「開 vad_filter / word_timestamps 只會拿到錯誤時間」（`:1373-1374`）。
- VAD 切段（`_nan_vad_windows()`，`:1412`）僅用於**台語模式與離線批次**，其視窗上限為 28 秒（`_NAN_WINDOW_SEC`，`:1382`），屬長音訊處理，非即時路徑。
- 其重疊去重不是字串前後綴比對，而是**相似度比對**（`is_duplicate()`，`:7937-7955`）：對最近 10 筆結果（`deque(maxlen=10)`）做子字串重疊度 > 70%、以及 `difflib.SequenceMatcher` 比值 > 0.6 的雙重判定，並以 `shorter >= 8` 避免短句誤判。

**決定**：即時路徑維持重疊滑動視窗，不導入 VAD。改為將現行的 `remove_overlap()`（前後綴精確比對）替換為相似度去重，並對最近 N 筆結果比對而非僅前一筆。

**理由**：滑動視窗重疊的本質是「同一段語音被辨識兩次且結果未必逐字相同」，前後綴精確比對在此情境下必然失效——這正是現行實作的缺陷所在。相似度比對直接對應該情境。VAD 對即時路徑的問題在於：等待靜音邊界本身就是延遲來源，且參考實作實測其時間戳在即時參數下不可靠。

**保留 VAD 的適用範圍**：伺服器端的批次流程已在使用 VAD（`server/app.py` 的 whisperx 路徑），不受本決定影響。

### 4a. 語速與延遲的關係

英文語速快不會使 3 秒視窗「追不上」，因為視窗是重疊的、且擷取與轉錄各自獨立：音訊持續寫入環形緩衝，不因轉錄較慢而遺失。真正的風險是轉錄耗時 > 步進時的**延遲累積**，這由決定 3 的背壓策略處理。

參考實作對此的處理方式可佐證：其以 `_MAX_CONCURRENT_TRANSCRIPTIONS` 限制同時進行的辨識數（`:7014-7019`），超過即跳過本輪；並在序列化鎖等待逾時（等於 step_sec）時直接放棄，註明「等太久不如放棄，下一個 chunk 有更新的音訊」（`:7897-7898`）。這與本變更決定 3 的丟棄最舊策略取向一致。

語速真正影響的是**單一視窗內的語意完整度**：語速越快，3 秒內塞入的字越多，跨視窗切斷語句的機率越高。因應方式是加長視窗（如參考實作的教育訓練 8 秒）而非縮短，代價是首次出字延遲增加。故視窗長度應為可調設定，並提供對應不同情境的預設組合。

### 5. 滑鼠穿透（已移出本變更範圍）

**最終歸屬**：此項對應基準需求「System allows interacting with content beneath the caption window」（隨 `add-live-caption-overlay` 於 2026-08-11 歸檔），非本變更新增，已自 proposal 移出。以下保留實作決定作為紀錄。

以 Tauri 的 `set_ignore_cursor_events()` 實作，但**未**採原先規劃的持久化開關，改為 session 級的「鎖定＝穿透」切換（不落盤）。原因：與既有的 `live_caption_click_through`（游標感應式自動穿透）語意重複。

切換入口置於字幕視窗自身的標題列，且 watcher 全程運作——鎖定時游標移入標題列／邊框仍恢復互動，故使用者不會被鎖在穿透狀態而無法關閉。

## Risks / Trade-offs

- **遠端主機不可用時即時字幕中斷**：4090 主機為區網或遠端服務，網路波動會直接反映為字幕中斷。緩解：沿用既有的單段失敗容錯（略過該段續行），僅在連續失敗時回報。
- **秒級逾時可能誤丟正常回應**：若 4090 主機負載高，正常回應也可能超過秒級逾時而被丟棄。緩解：逾時值設為可調設定，並在實測後決定預設值。
- **`auto` 語言偵測對短片段不穩**：即時路徑的短視窗可能不足以讓模型正確判斷語言。緩解：使用者可明確指定語言；此為預設值的取捨，非強制。

（原列的「VAD 引入新相依」風險已不適用：本變更決定不導入 VAD，見決定 4 與 tasks 4.4。）
