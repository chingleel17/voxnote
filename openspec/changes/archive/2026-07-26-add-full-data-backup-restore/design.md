## Context

目前 VoxNote 將結構化資料存於 `{app_data_dir}/voxnote.db`，錄音預設存於 `{app_data_dir}/recordings`，封存會議則可能存於 `{app_data_dir}/archives` 或使用者設定的自訂位置。`recordings.file_path` 與 `meetings.archived_path` 儲存絕對 Windows 路徑；直接複製資料到不同使用者帳號或不同磁碟後，資料庫仍會指向舊位置。`config.toml` 另含 API 金鑰與裝置偏好，不適合作為資料備份的一部分。

PRD 的 FR-062 已列出 ZIP 完整備份以及合併、覆蓋兩種匯入模式。本次需要將既有 SQLite 資料與檔案資產轉成可攜格式，並在不透過前端直接存取檔案系統的前提下，透過 Tauri command 完成。

## Goals / Non-Goals

**Goals:**
- 讓使用者從設定頁建立單一 ZIP 備份，保留會議資料、錄音與封存檔案。
- 讓備份可在不同 Windows 使用者帳號或不同電腦還原，不沿用來源電腦的絕對檔案路徑。
- 提供覆蓋還原與不覆寫既有會議的合併匯入，並回報成功、略過與缺少檔案的項目。
- 匯出與匯入全程由 Rust 後端處理，且不將任何 API 金鑰或裝置專屬設定寫入備份。

**Non-Goals:**
- 不實作單一會議分享檔、TXT/Markdown/PDF 匯出或雲端同步。
- 不備份或還原 `config.toml`、LLM/ASR 金鑰、模型檔與錄音裝置偏好。
- 不支援匯入 schema revision 不在目前程式明確支援範圍內的備份。
- 不在本次處理不存在於資料庫、但留在任意自訂資料夾中的孤立檔案。

## Decisions

### 1. 使用版本化 ZIP 加上 SQLite 快照與資產清單

備份 ZIP 使用固定結構：

```text
manifest.json
database.sqlite
assets/recordings/<recording-id>/<original-file-name>
assets/archives/<meeting-id>/...
```

`manifest.json` 包含格式版本、建立時間、來源應用程式版本、由備份模組定義的資料庫 schema revision、每個資產的 ZIP 相對路徑與對應資料列 ID。`database.sqlite` 是建立備份時產生的一致性快照，不含 `-wal` 或 `-shm` 檔。匯入前必須對資料庫快照執行完整性與外鍵檢查，且 revision 必須在程式明確支援的範圍內。匯入時一律以 manifest 內的相對路徑定位資產，絕不採用來源資料庫的絕對 `file_path` 與 `archived_path`。備份 ZIP 先寫至使用者選定位置同層的暫存檔，全部寫入、關閉並驗證成功後才以重新命名方式取代最終檔案；失敗時移除暫存檔且不覆蓋既有備份。

- **Why**：SQLite 快照可保留完整關聯式資料與未來欄位，manifest 則負責可攜資產位置、版本檢查與驗證；原子寫入可避免使用者誤把中斷產生的 ZIP 當成可還原備份。
- **Alternative considered**：只壓縮 AppData 資料夾，或只匯出 JSON。
- **Why not**：直接複製 AppData 會保留失效的絕對路徑與敏感設定；單一 JSON 需要重建並維護所有資料表序列化邏輯，較容易遺漏欄位。

### 2. 匯出前建立一致性的 SQLite 快照，再以資料庫列出的路徑收集資產

後端須以 SQLite 的備份或快照機制產生暫存資料庫檔，完成後讀取快照中的 `recordings.file_path` 與 `meetings.archived_path`，再將存在的錄音檔和封存目錄寫入 ZIP。任何遺失或無法讀取的檔案都不得使結構化資料遺失，但須列入完成結果的警告。

- **Why**：正在使用 WAL 的資料庫不可只複製主 `.db` 檔；由資料庫建立快照可避免遺漏尚在 WAL 的資料。
- **Alternative considered**：關閉應用程式後直接複製 `.db`、`-wal`、`-shm`。
- **Why not**：需使用者手動關閉應用程式，且不適合作為應用程式內的一鍵操作。

### 3. 匯入時將資產寫入目前 AppData 並重寫所有路徑

錄音統一還原至目前應用程式資料目錄的 `recordings` 子目錄；封存目錄還原至 `archives` 子目錄。目標檔名必須由 recording UUID 加上安全化的原始檔名組成，以避免不同來源的同名檔案互相覆寫。後端在寫入資料列時，使用還原後的絕對路徑取代來源快照中的路徑。若錄音或封存資產不存在，相關資料列仍可匯入，但檔案路徑須設為空值或不設定封存路徑，且結果必須明確回報。覆蓋還原僅會置換 AppData 內由 VoxNote 管理的 `recordings` 與 `archives` 目錄；來源或目的端的自訂外部儲存目錄只讀取其被資料庫引用的檔案，絕不刪除其中內容。

- **Why**：資料列使用目前電腦的路徑，使用者不必再以 SQL 修改帳號名稱或磁碟代號。
- **Alternative considered**：保留來源絕對路徑，或改動既有 schema 將所有路徑改為相對路徑。
- **Why not**：保留絕對路徑無法解決本次問題；全面 schema 重構會波及現有資料與既有封存功能，超出本次範圍。

### 4. 覆蓋還原與合併匯入採不同且可預期的衝突規則

覆蓋還原會在驗證 ZIP 後，以單一資料庫交易清除可還原的既有資料並寫入備份快照資料，再以暫存目錄完成檔案複製後置換受管理的 `recordings` 與 `archives` 資產。匯入開始後取得應用程式層級的資料操作鎖定，拒絕新的資料修改 command，並等待既有的資料修改工作完成後才進入交易；鎖定會在成功、失敗或 panic cleanup 後釋放。失敗時保留原有資料與資產。

合併匯入不覆寫目的端既有 UUID 相同的會議、逐字稿、摘要、錄音、範本與說話者對應，並將其計為略過；分類與標籤依名稱重用目的端資料列，常用參與者依名稱保留較高使用次數。匯入結果必須列出新增、略過、重用與警告的數量。

- **Why**：換電腦通常使用覆蓋還原；回收舊資料或整合兩台電腦時則需要不破壞現有紀錄的合併選項。
- **Alternative considered**：只提供覆蓋模式，或讓合併模式自動以欄位內容覆寫衝突資料。
- **Why not**：只提供覆蓋會阻礙整合；自動覆寫無法安全判定哪一份會議、逐字稿或摘要較新。

### 5. UI 放在設定頁並將不可逆操作分成選檔、預覽與確認

設定頁新增「資料備份與還原」區塊。匯出使用系統儲存檔案對話框；匯入先選擇 ZIP、顯示 manifest 驗證結果及預計新增/覆蓋的數量，再選擇合併或覆蓋並二次確認。匯入期間停用同一頁的資料操作並顯示進度或明確的處理中狀態；成功後重新取得目前頁面資料或重新載入路由，避免畫面保留匯入前的快取內容。

- **Why**：設定頁已集中資料儲存位置等進階操作；預覽與確認可降低覆蓋操作造成的誤用。
- **Alternative considered**：於首頁放置快捷按鈕，或選檔後立即匯入。
- **Why not**：首頁會增加非日常操作的干擾；立即執行無法安全處理覆蓋風險。

## Risks / Trade-offs

- **[備份期間資料變動造成不一致]** → 先建立 SQLite 快照，再只依快照讀取資料列與資產清單；匯出結果標示在快照建立後新增或刪除檔案可能未被包含。
- **[ZIP 損毀、惡意路徑或不相容版本]** → 匯入前驗證 manifest 格式版本、支援的資料庫 schema revision、SQLite 完整性與外鍵、所有 ZIP 項目路徑、資料庫與資產 ID 對應；拒絕絕對路徑、`..` 路徑穿越、符號連結與重複項目。
- **[惡意 ZIP 耗盡磁碟或記憶體]** → 預檢逐項計算宣告與實際解壓大小、檔案數量及目標 AppData 可用空間；超出可用空間或安全上限即拒絕，且僅串流讀寫檔案。
- **[覆蓋還原中斷導致資料遺失]** → 先完整解壓與驗證至 AppData 內的暫存目錄，使用資料庫交易及暫存資產交換；任何失敗均清理暫存內容並保留既有資料。
- **[封存檔案與錄音重複收錄增加 ZIP 容量]** → 初版以完整性優先收錄兩者，完成畫面顯示 ZIP 大小；跨資產去重留待後續需求。
- **[合併資料衝突難以完全自動解決]** → 僅自動重用具唯一名稱的分類、標籤與常用參與者；其餘 UUID 衝突一律略過並回報。
- **[匯入與轉錄、校稿或封存同時寫入]** → 匯入持有全域資料操作鎖定，既有工作完成後才開始，進行期間拒絕新的修改操作並在 UI 顯示需等待的狀態。

## Migration Plan

1. 新增後端備份模組、版本化 manifest 型別、ZIP 讀寫與 SQLite 快照建立流程。
2. 新增匯出、預檢與執行匯入的 Tauri commands、全域資料操作鎖定，並完成錄音與封存資產的相對路徑映射。
3. 在設定頁串接選檔、匯入模式、確認提示與結果回報。
4. 以含錄音、封存會議、缺失檔案、同名錄音、不同使用者路徑及外部自訂資料夾的資料庫測試備份和還原。
5. 若需回退，移除設定頁入口與 command 註冊即可；既有資料庫 schema 不變，現有資料不受影響。
