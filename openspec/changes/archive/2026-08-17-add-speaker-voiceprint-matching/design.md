## Context

VoxNote 的語者分離以錄音段落為單位執行，講者代號每段從 A 重新編號。使用者因此在兩個層面重複勞動：同一場會議的多個錄音段落各自指認一次，以及每場新會議從零開始指認固定成員。

`2026-07-26-use-meeting-participants-for-diarization` 已處理過相關議題（以與會人數提示 pyannote），其決策 4 原為 min=max 鎖定，後續實作改為僅傳 `max_speakers`（`asr/mod.rs:491-496`），理由記錄於程式碼註解：單一錄音段落未必所有人都發言，鎖死會迫使 pyannote 硬拆。本變更 MUST NOT 改動該策略——人數提示與聲紋比對是互補而非替代關係。

技術前提已驗證：WhisperX 的 `DiarizationPipeline.__call__` 支援 `return_embeddings=True` 並回傳 `(diarize_df, {speaker_id: embedding})`；pyannote community-1 以 `wespeaker-voxceleb-resnet34-LM` 產生 256 維 centroid。向量目前已被計算但在轉錄結束後丟棄。

## Goals / Non-Goals

**Goals:**

- 同一會議內跨錄音段落串接同一講者。
- 跨會議辨識既有參與者，減少重複指認。
- 比對結果經使用者確認後才生效。
- 模型變更時既有聲紋安全失效，不產生錯誤提議。

**Non-Goals:**

- 不自動套用比對結果。
- 不改動講者代號格式與 `recording_speaker_mappings` 的範圍設計。
- 不提供聲紋管理介面（第一版）。
- 不支援 AssemblyAI。
- 不以 LLM 進行語者校正。

## Decisions

### 決策 1：向量由服務端回傳，客戶端負責比對

服務端僅取出 `return_embeddings` 的結果並回傳，MUST NOT 於服務端保存或比對。理由：聲紋庫繫結使用者的本地資料庫與參與者名單，屬 app 層資料；服務端維持無狀態，與既有設計一致。

*替代方案*：服務端維護聲紋庫並直接回傳人名——會使服務端需存取會議資料，破壞現有職責分界，且服務可能為多個 app 實例共用。不採用。

### 決策 2：聲紋獨立資料表，繫結 `saved_participants`

新增聲紋表 `voiceprints`，以 `saved_participants.id` 為外鍵，並記錄產生模型識別、向量本體與建立時間。允許同一參與者多筆聲紋。

不將向量放入 `speaker_mappings` 或 `recording_speaker_mappings` 的新欄位：那兩張表以會議／錄音為範圍且每個 `speaker_label` 唯一，無法承載「一位參與者累積多筆聲紋」的關係。

建表使用 `CREATE TABLE IF NOT EXISTS` 加入 `MIGRATION_SQL`，符合既有慣例且不影響既有欄位。

#### 決策 2.1：轉錄完成到使用者確認之間的暫存層

`voiceprints` 表僅承載「已確認身分」的聲紋，繫結 `saved_participants`。但轉錄完成的當下尚無人名——三層比對（段落內合併、會議內串接、跨會議辨識）的前兩層完全不需要聲紋庫，只需要「這場會議這幾個錄音段落，各自有哪些講者代號、各自的向量」，且此資料需在使用者確認之前就可跨錄音段落、跨 app 重啟取用。

因此新增 `recording_speaker_embeddings` 表，鍵設計比照 `recording_speaker_mappings`：以 `(recording_id, speaker_label)` 唯一，記錄向量本體與模型識別。轉錄完成、附有向量時即寫入此表（不需使用者確認）；使用者確認講者對應時，系統另外將該筆向量複製一份寫入 `voiceprints` 並繫結對應的 `saved_participants`（決策 6 的寫入時機不變，僅資料來源改為讀取此暫存表）。

此表 MUST 納入 `backup.rs` 的備份還原範圍，比照 `recording_speaker_mappings` 隨錄音一併複製；還原後段落內合併與會議內串接的比對資料才不致遺失。

### 決策 3：模型識別為必要欄位且參與過濾

每筆聲紋記錄產生該向量的 diarization 模型識別。比對時 MUST 僅納入與當前模型相符者。

理由：`DIARIZATION_MODEL` 可經環境變數覆寫，不同模型的向量空間不可互比。若不記錄，模型變更後比對不會報錯，只會產生看似合理但實際錯誤的提議——這是靜默失效，比明確失敗危險得多。

模型變更後既有聲紋自動退出比對，使用者需重新累積。此為刻意取捨：安全失效優於錯誤提議。

### 決策 4：三層比對，由內而外依序執行

**段落內合併**：單一錄音段落內，pyannote 可能把同一人分群為多個代號（使用者實際遇到的問題）。以向量相似度提議合併。此層不需聲紋庫。

**會議內串接**：同一會議各錄音段落的講者向量互相比對，相似者串接為同一人。此層亦不需聲紋庫。

**跨會議辨識**：以本次向量比對聲紋庫，提議既有參與者人名。

三層皆為提議，且 MUST 由內而外依序執行——先確定「這幾個代號是同一人」，再問「這個人是誰」。若順序顛倒，使用者會被要求對同一個人的每個分裂代號重複回答身分。

段落內合併與 `improve-diarization-accuracy` 的分群門檻調整互補：門檻是事前預防，本層是事後補救。門檻無法對所有錄音都調到最佳，故兩者並存。

### 決策 5：相似度以 cosine 距離，門檻可設定

pyannote 的嵌入向量經 L2 正規化，cosine 距離範圍 0–2。門檻寫入 `AppConfig`，具保守預設值。低於門檻不提議，MUST NOT 退而提供最接近候選——寧可不提議，也不要讓使用者習慣性採納錯誤建議。

門檻的適當值需以實際會議錄音實測，第一版提供可調參數而非宣稱最佳值。

### 決策 6：聲紋於使用者確認講者對應時寫入

使用者在講者對應區確認「講者A 是 王小明」時，該講者的向量存入聲紋庫並繫結對應的 `saved_participants` 記錄。

不於轉錄完成時自動寫入：此時尚無人名，向量無從繫結。以使用者確認為寫入時機，可確保每筆聲紋都有經人工驗證的身分，避免錯誤標註污染聲紋庫並在後續比對中自我強化。

### 決策 7：向量的儲存格式

256 維 f32 向量以固定格式序列化為 BLOB 或文字欄位儲存。既有慣例中 ID 為 UUID 文字、時間為 ISO 8601 文字；向量無對應慣例，實作時擇一並於程式碼註解記錄，MUST 保持讀寫格式一致。

需納入 `backup.rs` 的備份還原範圍，並確認格式在備份合併流程中正確保留。

## Risks / Trade-offs

- **錯誤提議降低使用者信任** → 以保守門檻與人工確認緩解；寧可漏提議也不誤提議。
- **聲紋庫因錯誤確認而退化** → 寫入時機限於人工確認，降低但無法完全排除；第一版不提供刪除介面，若實測發現問題再評估補上。
- **僅本地 ASR 可用造成功能不一致** → 已與使用者確認可接受，AssemblyAI 維持現狀且不顯示相關 UI。
- **模型變更使既有聲紋失效** → 刻意取捨，安全失效優於錯誤提議。
- **同名不同人** → `saved_participants` 以 `name` 唯一，兩位同名參與者會共用聲紋記錄並產生混淆。此為既有資料模型的固有限制，本變更不處理，但實作時 MUST 於程式碼註解記錄此限制。

## Migration Plan

1. 服務端：啟用 `return_embeddings` 並於回應附上向量與模型識別；補測試。
2. Rust：新增聲紋表與 CRUD → 解析向量 → 會議內串接 → 跨會議比對 → 納入備份。
3. 前端：提議呈現與採納操作。
4. 以實際會議錄音實測門檻值。

**Rollback**：聲紋表可保留不用；服務端 `return_embeddings` 為附加欄位，客戶端忽略即回復原行為。
