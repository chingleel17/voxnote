## Context

`src/pages/record.ts` 現有「上傳音訊」使用 Tauri dialog 的 `multiple: false`，只保留一組 `uploadedFilePath` / `uploadedFileName` 狀態，先建立單檔預覽，再呼叫 `importRecordingFile()` 儲存並導向 `#meeting/{id}`。`src/pages/meeting.ts` 的錄音區塊則只提供「前往錄音」或「新增錄音段落」，兩者皆導向 `#record/{meetingId}`。

後端 `import_recording_file` 已能將一個來源檔直接從檔案系統複製至錄音儲存目錄，再由 `recording::create_recording()` 取得下一個 `sort_order` 建立段落。音訊不經 IPC 傳輸位元組，適合延續用於大檔案。本變更需跨越會議頁 UI、前端 API 與 Rust 檔案／資料庫操作，且必須處理批次部分成功的可恢復狀態。

## Goals / Non-Goals

**Goals:**

- 讓上傳工作階段完整存在於會議詳情頁，不觸發 hash route 切換。
- 以小型待上傳清單管理多個來源路徑，支援追加選擇、逐檔移除及全部取消。
- 保持檔案複製在 Rust 端執行，並依使用者看到的清單順序建立錄音段落。
- 讓批次結果可區分成功與失敗項目，使重試不會重複匯入成功檔案。
- 上傳完成後使用既有頁面重建流程同步錄音、逐字稿與段落控制狀態。

**Non-Goals:**

- 不把桌面錄音功能搬入會議詳情頁；本次行內操作僅處理既有音訊檔上傳。
- 不新增待上傳檔案的波形預覽、播放、拖曳排序或檔名編輯。
- 不自動開始轉譯、校稿或摘要生成。
- 不移除或改造錄音頁既有的單檔上傳／錄製流程。
- 不提供跨頁面或應用程式重啟後的待上傳工作階段復原。

## Decisions

### D1：在錄音區塊內建立行內待上傳面板

擴充 `buildRecordingSection()`，讓 header 永遠提供「上傳音訊」按鈕；按下後在同一 section 顯示待上傳面板。無既有錄音時不再以 early return 阻斷此入口，空狀態、待上傳面板及既有錄音清單由同一 section 管理。

面板持有 `{ sourcePath, originalFileName }[]`，檔案選擇器使用 `multiple: true`。再次選檔時附加至清單；以標準化後的完整來源路徑作為工作階段內識別值，相同路徑已在清單時略過，避免同一操作中誤選重複檔案。路徑只用於內部識別，畫面僅顯示原始檔名。

**替代方案：使用 modal。** Modal 也能避免跳頁，但錄音段落及上傳進度無法同時被看見，部分失敗後重試亦需維持 modal 狀態。行內面板更符合「在會議頁做這個操作」且能直接與更新後段落銜接。

### D2：新增單次 IPC 的批次匯入命令

新增 `import_recording_files`，接收 `meeting_id` 與依序排列的 items；每個 item 包含 `source_path`、由後端產生唯一目的檔名所需的原始檔名資訊。命令回傳逐檔結果，至少包含來源路徑、原始檔名、成功時的 `Recording`、失敗時的錯誤訊息。

後端在一次 `DataOperationLock` 寫入鎖期間依序處理 items。每一項重用抽出的單檔複製／建立錄音 helper；檔名由後端使用 UUID 或等價唯一值產生並保留支援格式的副檔名，避免前端用 `Date.now()` 在同一毫秒處理多檔造成覆寫。單項錯誤轉成該項結果後繼續下一項，不使整個 command 提前失敗；只有無法取得全域寫入鎖等批次開始前錯誤才拒絕整批。

**替代方案：前端對既有 `import_recording_file` 逐檔呼叫。** 雖然改動較小，但每次各自取得寫入鎖，可能被備份／還原穿插；目的檔名仍由前端負責且部分結果需從 rejected promise 自行拼裝。批次 command 能集中檔名、安全複製、順序與結果契約。

**替代方案：全有或全無交易。** 檔案系統複製與 SQLite 無法在目前架構下形成單一原子交易，回滾已複製檔案與已建立資料會增加失敗面；需求重點是減少重選，因此採逐項結果與可重試狀態。

### D3：成功項目立即提交，失敗項目留在前端清單

批次回傳後，前端以來源路徑對照結果：成功項目從待上傳狀態移除，失敗項目保留並顯示項目級錯誤。若至少一項成功，重新取得會議頁資料並重建相關 section；若仍有失敗項目，重建後恢復面板與失敗清單，讓使用者重試或移除。

不嘗試回滾成功項目。這使頁面狀態精確對應已落盤與已寫入 DB 的事實，也確保下一次儲存只傳送失敗項目。

### D4：重用會議頁既有 refresh 邏輯，不做整頁導覽

會議頁目前已在刪除、重排與轉譯後透過區塊重建更新狀態。上傳流程提供 `onUploaded` callback 給錄音 section，成功後由頁面層重新讀取 `getRecordings(meetingId)`，並重建錄音與依賴錄音資料的逐字稿區塊。不得設定 `window.location.hash`，因此網址、捲動脈絡與會議身分維持不變。

若重建整個錄音 section 會遺失失敗清單，待上傳狀態需由 `renderMeetingPage` 持有並傳回 section，而非只存在於被替換的 DOM 閉包。

### D5：支援格式沿用既有上傳集合

會議頁檔案選擇器沿用錄音頁現有副檔名集合：`wav`、`mp3`、`m4a`、`aac`、`flac`、`ogg`、`wma`。本變更不新增檔案大小限制；Rust 繼續以檔案系統複製處理，不將音訊載入 webview 記憶體。後端仍需檢查來源存在且為一般檔案，不能只依賴 dialog filter。

## Risks / Trade-offs

- **[部分成功造成使用者不確定目前狀態]** → 逐檔回傳結果、立即顯示成功段落，並只保留失敗項目與錯誤文字；toast 同時顯示成功／失敗數量。
- **[大批檔案使操作時間較長]** → 儲存期間鎖定待上傳清單與按鈕並顯示處理中狀態；音訊維持檔案系統複製，不做前端解碼或波形分析。
- **[同一路徑重複選取]** → 同一待上傳工作階段以標準化完整路徑去重；已經成功上傳後使用者日後再次主動選取同一來源仍視為新的錄音段落，不建立永久去重規則。
- **[批次處理期間頁面被導離]** → 後端命令會完成已開始的批次；前端回傳後僅在目前仍為同一會議頁時更新 DOM，避免寫入已卸載畫面。
- **[檔案複製成功但 DB 建立失敗留下孤兒檔]** → helper 在資料庫建立失敗時嘗試刪除該次新複製的目的檔；清理失敗記入該項錯誤，不影響其他項目。

## Migration Plan

此變更不需要資料遷移。部署為新增命令、型別、API wrapper 與會議頁 UI；既有 `import_recording_file` 及錄音頁流程保持可用。回滾時移除新批次命令與行內 UI，不影響已匯入的標準 `recordings` 資料及音訊檔。
